# Feature 0040: Admin poate crea utilizator cu rol INTRODUCER din Create User

## Summary

Un user admin trebuie să poată crea un cont cu rol **Introducer** din Backoffice → Users → Create User. În prezent acest flux nu funcționează corect: fie utilizatorul este creat dar redirecționat la sign-nda (nda_signed=false), fie apare o eroare. Scopul este ca admin-ul să poată crea direct un INTRODUCER (fără cerere de contact / NDA), similar cu MM (Market Maker).

**Detalii verbatim din cerere**: „un user admin poate sa creeze un cont cu role introducer. acum nu functioneaza”.

## Context (app_truth.md, ROLE_TRANSITIONS.md)

- **MM**: Admin creează din Backoffice → Users → Create User (rol MM); nu trece prin cereri de contact.
- **INTRODUCER** (documentat până acum): creat din cereri NDA cu `request_flow='introducer'`, apoi Approve & Create User cu `target_role=INTRODUCER`. Nu există documentație explicită pentru crearea directă de INTRODUCER de către admin (ca pentru MM).
- INTRODUCER are `entity_id=null`, acces la `/introducer/dashboard`; dacă `nda_signed=false`, frontend redirecționează la `/introducer/sign-nda`.

## Cauza problemei

- **Frontend**: `CreateUserModal` are deja INTRODUCER în dropdown-ul „Initial Role” (`frontend/src/components/users/CreateUserModal.tsx`). Formularul trimite `role: 'INTRODUCER'` la `POST /admin/users`.
- **Backend** `create_user` (`backend/app/api/v1/admin.py`):
  - Nu restricționează rolul; `UserCreate` acceptă orice `UserRole` (inclusiv INTRODUCER).
  - `ROLES_REQUIRING_ENTITY` nu include INTRODUCER → `entity_id` rămâne `None` pentru INTRODUCER (corect).
  - **Bug**: `nda_signed` este setat doar pentru TRODUCER: `nda_signed = user_data.role == UserRole.TRODUCER`. Pentru rol INTRODUCER, `nda_signed` rămâne `False` (default din model e True, dar în `create_user` se pasează explicit `nda_signed=nda_signed`). Rezultat: utilizatorul INTRODUCER creat de admin este redirecționat la `/introducer/sign-nda` în loc să aibă acces direct la dashboard.

## Fișiere și funcții de modificat

### Backend

| Fișier | Modificare |
|--------|------------|
| `backend/app/api/v1/admin.py` | În `create_user`: setați `nda_signed=True` când `user_data.role == UserRole.INTRODUCER` (nu doar pentru TRODUCER). Astfel, INTRODUCER creați direct de admin au acces imediat la dashboard, fără flux sign-nda. |

Algoritm în `create_user`:

1. Păstrați logica existentă: `ROLES_REQUIRING_ENTITY`, auto-create entity doar pentru rolurile din acel set; INTRODUCER nu e în set → `entity_id` rămâne `user_data.entity_id` (de obicei `None`).
2. Păstrați `referral_code` doar pentru PREINTRODUCER și TRODUCER.
3. **Modificare**: în loc de `nda_signed = user_data.role == UserRole.TRODUCER`, folosiți: `nda_signed = user_data.role in (UserRole.TRODUCER, UserRole.INTRODUCER)` (sau logică echivalentă) astfel încât atât TRODUCER cât și INTRODUCER creați de admin să aibă NDA considerat semnat (fără upload NDA).
4. Restul creării user (password sau invitation, commit, email) rămâne neschimbat.

### Frontend

- **Nicio modificare obligatorie** pentru a face fluxul să „funcționeze”: dropdown-ul conține deja INTRODUCER și payload-ul este corect. Opțional: la selectarea rolului INTRODUCER se poate afișa un scurt mesaj că utilizatorul nu va avea entity (ca pentru MM), dacă există un pattern similar pentru MM.

### Documentație

| Fișier | Modificare |
|--------|------------|
| `app_truth.md` | În secțiunea MM / Backoffice Create User: menționați că admin poate crea și utilizatori cu rol **INTRODUCER** (fără entity, acces introducer dashboard). |
| `docs/ROLE_TRANSITIONS.md` | La „Implicații” / INTRODUCER: adăugați că admin poate crea direct un user INTRODUCER din Backoffice → Users → Create User (similar MM), nu doar din Approve & Create User pe cereri introducer. |

## Consistență

- Stil backend: `datetime.now(timezone.utc)`, try/except cu rollback pentru DB, `handle_database_error` unde e cazul.
- Frontend: token-uri design (navy-*, emerald-*), fără slate-* / gray-*.
- User.role și ContactRequest.user_role rămân SSOT; nu se introduce logică suplimentară pe request_type sau status.

## Faze

- **Faza unică**: modificare backend (nda_signed pentru INTRODUCER în `create_user`) + actualizare scurtă a documentației (app_truth, ROLE_TRANSITIONS). Frontend poate rămâne neschimbat; opțional un hint în CreateUserModal pentru rol INTRODUCER.

## Notă

Dacă în teste sau în producție apare o eroare explicită la `POST /admin/users` (ex. 400/422) în loc de doar redirect la sign-nda, planul acoperă doar cauza cunoscută (nda_signed). Orice validare suplimentară care blochează rolul INTRODUCER în `create_user` sau în schema `UserCreate` trebuie lăsată permisă (schema acceptă deja orice `UserRole`).
